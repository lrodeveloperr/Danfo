## Q1. CI/CD: GitHub Actions, free macOS options, Godot CI, Unity CI, fastlane / Gradle Play Publisher

### Takeaway
For a private repo, build and test Android on GitHub-hosted Linux runners. The Free plan includes 2,000 minutes/month, and Linux costs $0.006/min after the free minutes. iOS needs a Mac, and the zero-cost Mac options are Xcode Cloud (25 compute hours/month, included with the Apple Developer Program) and Codemagic (500 macOS M2 minutes/month on a personal account). GitHub's macOS runners cost $0.062/min, about 10× Linux. The self-hosted-runner fee GitHub announced for 1 March 2026 was postponed, and GitHub's own docs (16 Oct 2026) still say self-hosted usage is free. Use fastlane 2.241.x for both stores: `supply`/`upload_to_play_store` for Play, `pilot` for TestFlight, and `match` with an App Store Connect API key for signing. It is actively maintained. Gradle Play Publisher is in maintenance mode.

**GitHub Actions pricing (current docs, 16 Oct 2026 source commit)**
- Actions usage is **free for self-hosted runners and for public repositories** using standard GitHub-hosted runners. Private repos get a per-plan quota of minutes, artifact storage and cache storage. Usage beyond the quota is billed to the repository owner. — [GitHub Docs: GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) (read from the [github/docs source](https://github.com/github/docs/blob/main/content/billing/concepts/product-billing/github-actions.md))
- Included quotas for private repos: **GitHub Free (personal): 2,000 min/month, 500 MB artifact storage, 10 GB cache per repo**. Pro: 3,000 min, 1 GB. Free for organizations: 2,000 min, 500 MB. Team: 3,000 min, 2 GB. Enterprise Cloud: 50,000 min, 50 GB. — [GitHub Docs: Actions billing (included quotas reusable)](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- Standard runner per-minute rates: Linux 1-core $0.002. **Linux 2-core x64 $0.006**. Linux 2-core arm64 $0.005. Windows 2-core $0.010. **macOS 3- or 4-core (M1 or Intel) $0.062**. Larger runners: macOS 12-core $0.077, macOS 5-core M2 Pro (`macos_xl`) $0.102. — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- The old "minute multipliers" page (`/billing/reference/actions-minute-multipliers`) now redirects to the per-minute "Actions runner pricing" reference. GitHub has moved to per-SKU dollar rates, and the billing dashboard "may show your Actions usage as a dollar amount ('spend') rather than raw minutes." — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing); [GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- Larger runners are always charged, even for public repos, and included minutes cannot be used for them. — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- Overage storage: artifacts and Packages $0.25/GB-month, Actions cache $0.07/GB-month. With no payment method on file, usage is **blocked** when the quota runs out. — [GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- Concurrency on standard hosted runners: Free plan 20 concurrent jobs, **max 5 concurrent macOS jobs**. Pro 40/5. Each hosted job can run at most 6 hours. — [GitHub Docs: Actions limits](https://docs.github.com/en/actions/reference/limits)
- 2025–26 changes: GitHub announced on 16 Dec 2025 that hosted-runner prices would fall on 1 Jan 2026 (by "up to 39%" depending on machine type). It also announced a **$0.002/min platform charge for self-hosted runners from 1 March 2026**. — [GitHub Changelog, 16 Dec 2025](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/); [DevClass, 17 Dec 2025](https://devclass.com/2025/12/17/github-to-charge-for-self-hosted-runners-from-march-2026/)
- The self-hosted fee was **postponed** within about 48 hours after backlash, "to re-evaluate our approach". Some secondary sources still describe it as live, but the more recent and detailed ones say it never took effect. — [SAMexpert](https://samexpert.com/github-actions-pricing-backlash-2026/); [Tenki](https://tenki.cloud/blog/github-actions-runner-pricing-2026). The current GitHub Docs (source commit 16 Oct 2026) still state that self-hosted usage is free — [GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

**Free macOS build options**
- **Xcode Cloud: 25 compute hours/month included with Apple Developer Program membership.** Paid tiers are 100 h $49.99/mo, 250 h $99.99/mo, 1,000 h $399.99/mo and 10,000 h $3,999.99/mo. A compute hour is "an hour of time used to execute a specific task in the cloud, such as building an app or running automated tests". Getting started means you "configure a workflow in Xcode". — [Apple: Xcode Cloud](https://developer.apple.com/xcode-cloud/)

Three hooks exist: `ci_post_clone.sh`, `ci_pre_xcodebuild.sh` and `ci_post_xcodebuild.sh`. Scripts must be executable, and the default shell is zsh. A post-clone script can be used "to install an additional tool". — [Apple: Writing custom build scripts](https://developer.apple.com/documentation/xcode/writing-custom-build-scripts); [Apple Developer Forums thread 807674](https://developer.apple.com/forums/thread/807674) (a script at the repo root, not beside the project, was not detected)
- The Xcode Cloud build environment includes macOS/Xcode tools such as Python, plus **Homebrew** "to install dependency managers". Supported SCM providers are GitHub/GitHub Enterprise, GitLab and Bitbucket Cloud/Server. — [Apple: Making dependencies available to Xcode Cloud](https://developer.apple.com/documentation/xcode/making-dependencies-available-to-xcode-cloud); [Apple: Source code management setup](https://developer.apple.com/documentation/xcode/source-code-management-setup)
- For generated projects such as XcodeGen or Expo prebuild, a common pattern is to generate the Xcode project in `ci_post_clone.sh`. Nothing Godot- or Unity-specific was found. — [polpiella.dev](https://www.polpiella.dev/xcode-cloud-scripts-fastlane-and-cocoapods/); [richinfante.com](https://www.richinfante.com/2024/11/18/running-expo-prebuild-in-xcode-cloud)

### Inferences
- **Recommended Godot path (zero cost)**:
  - (1) **PR/push CI on `ubuntu-latest`**: run the `barichello/godot-ci:4.7.2-stable` container (pin the exact tag), or set up your own Godot 4.7.2 headless + templates. Run GUT/gdUnit4 tests, then `godot --headless --export-release "Android" build/danfo.aab` with the `GODOT_ANDROID_KEYSTORE_RELEASE_*` env vars fed from secrets (keystore base64-decoded at runtime). Upload with fastlane `supply` to the internal track.
  - (2) **iOS**: generate the Xcode project with `export_project_only=true` and build/sign with fastlane on a Mac runner. Which Mac to use, in order of cost:
    - (a) **Xcode Cloud** (1,500 free minutes/month). Commit a generated Xcode project directory containing `ci_scripts/ci_post_clone.sh`, which downloads the Godot macOS editor and templates (Homebrew/curl) and re-exports the `.pck`/project before `xcodebuild`.
    - (b) **Codemagic** personal (500 M2 min/month), with a custom shell workflow.
    - (c) GitHub `macos-latest` at $0.062/min.
  - Godot's docs require macOS for iOS export. Plan for the Godot export step itself to run on the Mac runner, not on Linux.
- The barichello/godot-ci Dockerfile pins Android `platforms;android-33`/`build-tools;33.0.2`/NDK r25. A Gradle-based Godot export (needed for Sentry, Firebase and Play Games plugins) will likely need newer SDK platforms to satisfy Play's current target-API rule. Expect to add `sdkmanager "platforms;android-35"` (or whatever Godot 4.7's template targets) in CI. This is not verified, so check the Godot 4.7 Gradle template.
- On the Free plan, if included minutes are valued at the Linux rate in dollar terms, 2,000 included minutes (~$12) would buy only about 190 macOS minutes. Treat macOS-on-GitHub as paid, and keep it off every-push triggers: tag/release only. This reading of how included minutes apply to macOS SKUs is an inference. See Gaps.
- **Unity path**: GameCI unity-test-runner and unity-builder on Ubuntu for Android/iOS player builds. The Xcode project goes to a Mac (Xcode Cloud, Codemagic, which has first-class Unity workflows, or `macos-latest`) for fastlane `match`/`gym`/`pilot`. A Unity Personal licence works via a `.ulf` secret.
- AI-agent workflow: every step above runs headless from Linux containers except the Mac signing/build step. Agents can author `Fastfile`, workflow YAML and `ci_post_clone.sh`, but someone has to set up the Xcode Cloud product/workflow once. Apple's Xcode Cloud page says you "configure a workflow in Xcode", which implies a one-time Mac (borrowed or rented) for onboarding. Not verified whether App Store Connect alone can create the first workflow.
- Choose fastlane over GPP: GPP is in maintenance mode and needs a Gradle host project. fastlane `supply` works on any AAB from any engine.

## Q2. Automated testing and device testing (incl. TestFlight, Play testing tracks, recruiting Nigerian testers)

### Takeaway
For Godot, use **GUT 9.7.1** (Godot 4.7) or **gdUnit4 6.2.2** (Godot 4.5–4.7.1, with an official GitHub Action and JUnit/HTML reports) for headless unit tests on Linux CI. Godot physics is officially **not deterministic**, so regression tests should drive game logic with fixed timesteps and recorded inputs, compare state with tolerances, and use `--write-movie --fixed-fps` for visual captures. Real-device coverage is free through Firebase Test Lab's Spark quota (10 virtual + 5 physical tests/day). Play's pre-launch reports and TestFlight (100 internal / 10,000 external testers) are also free. A new personal Play account must keep **12 testers opted in for 14 consecutive days** in a closed test before production access.

### Cited Findings
- **GUT**: versions 9.x are for Godot 4. **v9.7.1 (tag date 2026-07-09) targets Godot 4.7.x**, 9.6.1 targets 4.6.x and 9.5.0 targets 4.5.x. It has a CLI and exports results as **JUnit XML**, with doubles/stubs/spies and parameterised tests. — [bitwes/Gut README](https://github.com/bitwes/Gut)
- **gdUnit4** (repo now under `godot-gdunit-labs`): **v6.2.2 (tag date 2026-10-07)**. v6.2.x supports Godot 4.5–4.7.1, and master (v7.0.0) targets 4.7/4.7.1/4.8.dev7. Features: headless CLI for CI, HTML and JUnit XML reports, input simulation including touch, scene runner, mocking. — [gdUnit4 README](https://github.com/godot-gdunit-labs/gdUnit4)
- **gdUnit4-action** `godot-gdunit-labs/gdUnit4-action@v1` (latest tag v1.3.2) takes `godot-version`, `paths`, `timeout`, `godot-net` (C#), `publish-report` and `upload-report`. — [gdUnit4-action README](https://github.com/godot-gdunit-labs/gdUnit4-action)
- Godot docs: "Physics in Godot, regardless of physics engine, is **not** deterministic … not guaranteed to run the same way for seemingly identical situations." **Jolt is the default physics engine for new projects** (built in since 4.4). — [Godot docs: Physics introduction](https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html); [Godot docs: Using Jolt Physics](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)
- Godot CLI testing aids: `--fixed-fps <fps>` "disables real-time synchronization". `--write-movie <file>` renders offline (forcing fixed FPS). `--quit-after <n>` exits after n iterations. Movie Maker is documented for "comparing the visual output of graphics settings, shaders, or rendering techniques". — [Godot docs: Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html); [Godot docs: Creating movies](https://docs.godotengine.org/en/stable/tutorials/animation/creating_movies.html)
- **Firebase Test Lab quotas**: Spark (no-cost) allows **10 virtual-device and 5 physical-device test runs per day**. Blaze includes **60 min/day virtual and 30 min/day physical** at no cost, then **$1/device-hour virtual and $5/device-hour physical**. — [Firebase: Test Lab usage, quotas and pricing](https://firebase.google.com/docs/test-lab/usage-quotas-pricing); [Firebase pricing](https://firebase.google.com/pricing) (via search summary; host not fetchable)
- **Play closed-testing requirement**: personal developer accounts created after **13 Nov 2023** must run a closed test with **at least 12 testers opted in continuously for the 14 days** before applying for production access. — [Play Console Help 14151465](https://support.google.com/googleplay/android-developer/answer/14151465) (via search summary). The minimum was cut from 20 to 12, dated 11 Dec 2024 by one source, while another says 2025 — [PrimeTestLab](https://primetestlab.com/blog/google-play-changed-20-to-12-testers). A tester who opts out and back in restarts their continuous period — [dev.to analysis](https://dev.to/charleshartmann/google-plays-12-tester-rule-read-carefully-what-continuously-for-14-days-really-means-4km). Organisation accounts are reported exempt — [testerscommunity](https://www.testerscommunity.com/blog/google-play-12-testers-policy)
- **TestFlight**: up to **100 internal testers** (with ASC roles) and **10,000 external testers**. The first external build needs **TestFlight App Review**. Public invitation links can carry device/OS criteria. Up to 100 builds are shareable, with 30 devices per tester. Testers can send screenshot feedback, and crash reports come back to you. — [Apple: TestFlight](https://developer.apple.com/testflight/)
- Play's in-app review cannot be fully exercised outside Play-distributed builds. Reviews from closed-track users are shared privately with the developer instead of being public. — [Android: In-app reviews](https://developer.android.com/guide/playcore/in-app-review)

### Inferences
- **Test pyramid for Danfo (Godot)**:
  - (1) Pure-logic unit tests in GUT or gdUnit4 covering fares, route/stop logic, economy, save serialisation and migration, ad-pacing rules. Run them on every push in about 1–3 Linux minutes.
  - (2) Scene/integration tests with gdUnit4's scene runner and input simulation.
  - (3) **Replay tests**: record input streams (touch/steer/brake per physics tick) from playtests and replay them with `--headless --fixed-fps 60 --quit-after N`. Assert on gameplay invariants (passengers delivered, money, no stuck states, no errors) with tolerances, never bit-exact positions, since physics isn't deterministic.
  - (4) **Screenshot comparison**: render fixed camera shots with `--write-movie` (PNG sequence) or `get_viewport().get_texture().get_image()`, then compare with a perceptual-diff threshold on a pinned GPU/driver. Software rendering in CI is not the same as phones, so treat diffs as advisory.
- **Device testing**: Firebase Test Lab **Game Loop** tests suit games better than Robo/Espresso, because the app scripts its own demo run. Within the Spark quota that allows a nightly smoke run on 5 physical devices. Pick low-end Android devices typical in Nigeria (2–4 GB RAM, Mali/Adreno GPUs). Play pre-launch reports run automatically on testing-track uploads at no cost (see Gaps for specifics).
- **Recruiting Nigerian testers for the 12×14 rule**: build a 20–30 person Google Group from friends/family, Lagos danfo commuters, Nigerian gaming communities (WhatsApp/Telegram groups, X/Twitter, Nairaland gaming board, campus groups), and Discord. Use a Google Group as the tester list so one opt-in link covers everyone. Over-recruit by about 2× because of drop-outs, and remind testers not to opt out. Paid "12 testers" services exist but carry policy risk. The engagement quality Google asks about in the production-access questionnaire matters. These recommendations are not from a cited source.
- iOS has no equivalent gate. A public TestFlight link plus WhatsApp distribution suits Nigerian iPhone users, who are a small share of the market, so iOS testing can be lighter.

## Q3. Crash reporting: Crashlytics, Sentry Godot SDK, Unity Cloud Diagnostics, native symbolication

### Takeaway
**Sentry's official Godot SDK (v2.3.0, 29 Sep 2026; requires Godot 4.5+; Android, iOS and more)** is the best-supported crash reporter for Godot. It captures native crashes and GDScript errors, and it is a first-party GDExtension. Readable native stack traces need **custom-compiled Godot export templates with debug symbols**, uploaded with `sentry-cli`. Firebase Crashlytics works for Godot only through third-party plugins. For Unity, Firebase Crashlytics (Firebase Unity SDK 14.0.0, Oct 2026) or Sentry Unity (4.10.3) are the mainstream choices.

## Q4. Analytics and remote config for an ads-only game (Firebase/GA4, GameAnalytics, Unity Analytics; privacy)

### Takeaway

  - First-time-user funnel: `tutorial_step_n`, `first_route_complete`.

## Q5. Saves: local robustness, Android Auto Backup, Play Games Saved Games, iCloud/Game Center, cross-platform transfer

### Takeaway
Make local saves bulletproof first: atomic temp-then-rename writes, a versioned schema with migrations, a checksum, and the last N good saves kept. Then get **free, account-less backup on both OSes**:
- **Android Auto Backup** gives up to 25 MB per app on the user's Google Drive, automatic and restored on reinstall. Godot exposes it via the `user_data_backup/allow` export option.
- **iOS device/iCloud backup** covers app data. **iCloud key-value store** (1 MB, 1,024 keys) can sync a compact save across Apple devices, and Godot's official iOS iCloud plugin wraps it.
- **Play Games Services v2 Saved Games** (3 MB blobs, automatic sign-in) is optional explicit cloud save on Android.

Cross-platform transfer between Android and iOS isn't possible through any first-party service without a backend. The zero-backend option is a player-initiated export/import transfer code.

### Cited Findings
- **Android Auto Backup**:
  - **25 MB per app**, stored in a private folder on the user's Google Drive that "does not count toward the user's personal Google Drive quota". Only the latest backup is kept, end-to-end encrypted on Android 9+ with the screen lock.
  - Runs when ≥24 h since the last backup, the device is idle, and it is on Wi-Fi (unless the user opted into mobile data). It uploads only if data changed.
  - Default includes cover shared prefs, `getFilesDir()`, `getDatabasePath()` and `getExternalFilesDir()`. Cache/no-backup dirs are excluded. Include/exclude via `dataExtractionRules` (Android 12+) and `fullBackupContent` (≤11).
  - Over 25 MB, `onQuotaExceeded()` is called and no cloud backup happens. **Restore runs automatically when the app is installed** (Play Store, device setup or adb), before first launch. Device-to-device transfer is configured separately.
  - — [Android: Back up user data with Auto Backup](https://developer.android.com/identity/data/autobackup)
- **Key/Value backup** is limited to **5 MB per user**, needs a `BackupAgent` and `dataChanged()` calls, and "Most apps should use Auto Backup". An app can use one or the other, not both. — [Android: Key-value backup](https://developer.android.com/identity/data/keyvaluebackup)
- **Godot**: the Android export option `user_data_backup/allow` — "If `true`, allows the application to participate in the backup and restore infrastructure." On mobile, the `user://` path "is unique to the project and is not accessible" to other apps. — [Godot docs: EditorExportPlatformAndroid](https://docs.godotengine.org/en/stable/classes/class_editorexportplatformandroid.html); [Godot docs: Data paths](https://docs.godotengine.org/en/stable/tutorials/io/data_paths.html)
- Godot file APIs useful for robustness: `FileAccess.create_temp()`, `flush()` (files are only auto-closed on normal exit, so flush periodically), and static `FileAccess.get_sha256(path)`/`get_md5(path)` for checksums. — [Godot docs: FileAccess](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html)
- **Play Games Services v2 Saved Games**: a save is an unstructured binary blob plus metadata (name, description, last modified, played time, optional cover image). **Max 3 MB data, 800 KB cover image**. Any number of saves per player. Recommended practice: load the latest from the service on start/resume, save at a reasonable frequency, and let the user resolve conflicts. Guest-mode progress "is not saved or restored". Saved Games must be enabled in Play Console. — [Android: PGS Saved Games](https://developer.android.com/games/pgs/savedgames)
- **PGS v2 sign-in is automatic at launch**: "Play Games Services doesn't require a manual Sign in button." v21.0.0+ adds `SUPPRESS_GAME_PROFILE_CREATION`. — [Android: PGS v2 sign-in](https://developer.android.com/games/pgs/android/android-signin)
- **Godot Play Games Services plugin** (godot-sdk-integrations/godot-play-game-services): Godot 4.3+ (badge: Godot 4.5, Android API 35, **PGS v2 21.0.0**). Node-based API covering sign-in, leaderboards and **snapshots**. Latest tag **v3.4.0 (2026-07-20)**. — [godot-play-game-services README](https://github.com/godot-sdk-integrations/godot-play-game-services); [tags](https://github.com/godot-sdk-integrations/godot-play-game-services/tags)
- **iCloud key-value store (`NSUbiquitousKeyValueStore`)**: "no more than **1024 keys**". "The total amount of available storage space for all values is **1 megabyte**". Max value is 1 MB and max key length is 128 chars. Writes over the limits fail. Data is stored unencrypted, so don't store sensitive data. It requires App Store distribution and the iCloud KV entitlement. Changes sync across the user's devices with a change notification. — [Apple: NSUbiquitousKeyValueStore](https://developer.apple.com/documentation/foundation/nsubiquitouskeyvaluestore)
- **Godot official iOS plugins** include an **iCloud** plugin that wraps `NSUbiquitousKeyValueStore` (`set_key_values`, `get_key_value`, `synchronize_key_values`) and a **GameCenter** plugin (GameKit). Plugins are built as xcframeworks and enabled in the iOS export preset. — [godot-ios-plugins README](https://github.com/godot-sdk-integrations/godot-ios-plugins); [icloud.gdip](https://github.com/godot-sdk-integrations/godot-ios-plugins/blob/master/plugins/icloud/icloud.gdip); [gamecenter.gdip](https://github.com/godot-sdk-integrations/godot-ios-plugins/blob/master/plugins/gamecenter/gamecenter.gdip)
- **Game Center saved games (GameKit)**: `saveGameData(_:withName:)`, `fetchSavedGames`, `loadData` and `resolveConflictingSavedGames`. "To save a game, the player must have an iCloud account and **enable iCloud Drive**." The app needs the iCloud capability with **iCloud Documents** checked. Conflicts arise from the same filename saved on multiple devices, and the app must resolve them. — [Apple: Saving the player's game data to an iCloud account](https://developer.apple.com/documentation/gamekit/saving-the-player-s-game-data-to-an-icloud-account); [Apple: GKSavedGame](https://developer.apple.com/documentation/gamekit/gksavedgame)

### Inferences
- **Local save design (both engines)**:
  - (1) One JSON or binary `save.dat` under `user://` (Godot) or `Application.persistentDataPath` (Unity). Use an envelope `{schema_version, app_version, saved_at, payload, sha256(payload)}`.
  - (2) **Atomic write**: write to `save.tmp`, flush/close, verify by re-reading and checking the hash, rotate `save.dat` → `save.bak1` (keep 2–3 generations), then rename `save.tmp` → `save.dat` (Godot: `DirAccess.rename_absolute`).
  - (3) On load: try `save.dat`, fall back to `.bak1`/`.bak2` on hash or parse failure, and report a non-fatal to Sentry.
  - (4) Run **migrations** step by step from `schema_version` n to n+1, with unit tests holding golden saves from each shipped version.
  - (5) Save at safe points (route end, menu, `NOTIFICATION_APPLICATION_PAUSED`/focus-out on mobile). Never save mid-frame on the main thread when the file is large.
  - (6) Keep saves small (well under 1 MB) so they fit iCloud KVS and PGS limits as well as the 25 MB Auto Backup cap.
- The default Godot Android `user://` likely sits in internal app storage under `getFilesDir()`, which Auto Backup includes by default. That would make Auto Backup zero-code once `user_data_backup/allow=true`. This is not verified, so test with `adb shell bmgr backupnow <pkg>` and a reinstall. Exclude caches and large downloaded content.
- **What best-in-class offline mobile games tend to do** (general industry practice, not sourced this session): rely on OS backup by default, offer optional platform cloud save (PGS snapshots / Game Center or iCloud) behind a "Cloud save" toggle with a clear conflict UI ("Keep this device / Keep cloud: shows progress, money, last played"), and offer a **transfer/backup code** for cross-platform moves.
- **Cross-platform without a backend**: there is no shared Google↔Apple save store. Options:
  - (a) An export/import "transfer code": compressed, checksummed, base64/QR save that the player copies via WhatsApp or notes.
  - (b) A user-owned file (Share sheet to Drive/Files, then import).
  - (c) Accept per-platform progress.
  - Option (a) suits a Nigerian audience (WhatsApp sharing). Sign or HMAC the code to deter casual editing. That is not tamper-proof, which is acceptable since there are no IAPs.
- Danfo has no IAPs, so a lost save costs player goodwill but no money. That supports the "Auto Backup + iCloud backup by default, PGS/Game Center optional" approach over building a backend.

### Gaps
- iOS: Apple's current guidance on which app directories iCloud device backup covers (Documents/Application Support vs Caches), and where Godot's iOS `user://` maps. Not fetched this session.
- CloudKit free quotas (public/private database) for 2026. Not fetched. CloudKit would also need custom native code in Godot.
- Whether the Godot GameCenter plugin exposes GKSavedGame APIs. Not verified.
- PGS v1 deprecation and removal dates (the `/games/pgs/deprecation` page was not fetched).

## Q6. Release strategy: tracks, staged rollout, soft launch, pre-registration, ASO, In-App Review/Updates, update cadence

### Takeaway
Ship Android through internal → closed (meeting the 12-tester/14-day gate for a new personal account) → open → production with staged rollout. fastlane `supply` automates tracks, `rollout` fractions and in-app-update priority. iOS goes TestFlight internal → external (public link) → App Store with 7-day phased release (1→2→5→10→20→50→100%). Soft-launch in Nigeria first (the home market, with a cheap UA and ad-revenue baseline), optionally adding Ghana/Kenya for English-speaking African signal. Watch the Android vitals thresholds (1.09% crash, 0.47% ANR). The App Store has **no Nigerian Pidgin, Yoruba, Hausa or Igbo localization**, and Nigeria's storefront defaults to English (U.K.), so Pidgin can only appear inside English listing copy.

### Cited Findings
- fastlane `supply` supports `track`, `rollout` (e.g. `0.5`), `track_promote_to` and `in_app_update_priority`. Release lanes can use `track: 'rollout', rollout: '0.5'`. — [fastlane docs: supply](https://docs.fastlane.tools/actions/supply/); [fastlane docs: Android release deployment](https://docs.fastlane.tools/getting-started/android/release-deployment/)
- **App Store phased release**: 7 days at **1%, 2%, 5%, 10%, 20%, 50%, 100%**. It applies to users with automatic updates. You can pause for up to **30 days total**, with no limit on the number of pauses. Anyone can still manually download the update. — [App Store Connect Help: Release a version update in phases](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases)
- TestFlight limits: 100 internal and 10,000 external testers, public links, Beta App Review for the first external build. — [Apple: TestFlight](https://developer.apple.com/testflight/)
- **Android vitals**: crash 1.09% / ANR 0.47% overall bad-behaviour thresholds (8% per phone model). Play "may reduce the visibility" and show listing warnings. 28-day window. Issues that affect devices for over 7 days are flagged as emerging. — [Android vitals](https://developer.android.com/topic/performance/vitals)
- **In-App Review (Play)**: needs Play Core library ≥1.8.0 and Android 5.0+ with the Play Store. Google enforces a time-bound quota: calling more than once in a short period, "for example, less than a month", may show nothing. Don't trigger it from a button or call-to-action. Don't ask "Do you like the app?" before or while showing the card. Don't modify or overlay the card. Official integrations: Kotlin/Java, Native C++, Unity, Unreal (no Godot). — [Android: In-app reviews](https://developer.android.com/guide/playcore/in-app-review)
- **In-App Updates (Play)**: flexible (background download) vs immediate (fullscreen, required) flows. Android 5.0+, phones/tablets/ChromeOS. Not compatible with OBB expansion files. Official integrations: Kotlin/Java, Native, Unity, Unreal. — [Android: In-app updates](https://developer.android.com/guide/playcore/in-app-updates)
- **App Store localizations**: English variants are Australia, Canada, U.K. and U.S. **No Nigerian Pidgin, Yoruba, Hausa, Igbo or Swahili.** The Nigeria, Kenya and Tanzania storefronts default to **English (U.K.)** with no additional languages. — [App Store Connect Help: App Store localizations](https://developer.apple.com/help/app-store-connect/reference/app-store-localizations)
- The Play 12-testers/14-days gate (Q2) must be cleared before the first production release on a new personal account. — [Play Console Help 14151465](https://support.google.com/googleplay/android-developer/answer/14151465)

### Inferences
- **Android sequence**:
  - Weeks 0–2: internal testing (up to 100 testers, instant availability), with CI auto-upload of every `main` build.
  - Weeks 2–4+: closed testing with 20–30 Nigerian testers for ≥14 consecutive days. Collect private reviews and pre-launch reports, and fix ANRs and crashes on low-RAM devices.
  - Optional: open testing in Nigeria to gather scale signal.
  - Production: staged rollout 5% → 20% → 50% → 100% over about a week, halting if vitals or Sentry show regressions.
- **Soft launch geography (suggested, not sourced)**:
  - **Nigeria itself** is the natural soft-launch market. The theme (Lagos danfo) is home-market content, eCPMs are low but that's representative of the target, and the developer can talk to players directly.
  - **Ghana and Kenya** add English-speaking, Android-heavy African markets with similar device profiles to test whether the theme travels.
  - A tier-1 English market (e.g. UK, for the Nigerian diaspora) later tests ad-revenue upside.
  - Gate the global launch on D1/D7 retention and ARPDAU from ads.
- **Pre-registration**: Play pre-registration can collect installs before launch and auto-install on release (see Gaps for rules). On iOS, a pre-order for a free app serves the same role. It is worth running for 2–4 weeks around the Nigerian launch with social content (danfo conductor calls, Pidgin humour).
- **ASO baseline**:
  - English listing with Lagos/danfo keywords. Short description mixing English and Pidgin phrases ("Oya enter! Drive your danfo for Lagos").
  - 6–8 portrait screenshots with large text that reads on low-end phones, a 30-second gameplay video, a feature graphic, and a small APK/AAB size (users on metered data).
  - On iOS, only English (U.K.)/(U.S.) metadata is possible. Pidgin goes in the copy, not as a locale.
  - Whether Play Console lists Yoruba/Hausa/Igbo/Pidgin locales is unverified (Gaps).

## Q7. Large binary assets on GitHub: Git LFS quotas, pricing, alternatives; asset licence register

### Takeaway
On GitHub Free/Pro, Git LFS includes **10 GiB storage + 10 GiB bandwidth per month**, metered billing replaced data packs, and **every CI checkout of LFS files consumes bandwidth**. A 3D game with art in LFS can blow through 10 GiB of bandwidth quickly if CI pulls LFS on every run. Keep large source art (.blend, .psd, raw audio) outside the code repo, and commit only engine-ready, compressed assets. Use LFS selectively with CI caching, and set a $0 budget so overages block instead of billing.

### Cited Findings
- Git LFS included usage: **Free and Pro: 10 GiB bandwidth/month + 10 GiB storage**. Team and Enterprise Cloud: 250 GiB + 250 GiB. — [GitHub Docs: Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs) (values from the github/docs `large_files.yml` variables)
- "Previously, Git LFS billing used pre-paid data packs. These have been **removed and replaced with metered billing**." Storage accrues hourly, and every pushed version counts in full (a 1-byte change to a 500 MB file adds another 500 MB). Downloads count against the **repository owner's** bandwidth, **including GitHub Actions downloads**. Archives that include LFS objects also count. — [GitHub Docs: Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)
- With the **budget at $0**, overage is not charged but LFS usage is blocked for the rest of the month. Over the storage quota without payment you can still clone (pointer files only) but can't push. Over the bandwidth quota, LFS is disabled until next month. — [GitHub Docs: Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)
- Max LFS file size: Free/Pro 2 GB, Team 4 GB, Enterprise Cloud 5 GB. Regular git file limit is 100 MiB (warning at 50 MiB). — [GitHub Docs: About Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)
- Actions cache: 10 GB per repo included. Artifacts are capped at 500 MB on Free (personal). — [GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- GameCI's sample workflows check out with `lfs: true` and cache the Unity `Library` folder. — [GameCI: Getting started](https://game.ci/docs/github/getting-started)

### Inferences
- **Budget math (rough)**: if the engine-ready asset set in LFS is 2 GiB, then 5 full CI checkouts already use 10 GiB, the whole monthly free bandwidth.
  - Mitigations: use `actions/checkout` with `lfs: false` plus a cache keyed on `git lfs ls-files -l` hashes, then `git lfs pull` only on cache miss.
  - Run asset-heavy jobs only on release tags.
  - Keep LFS for binaries Godot imports (`.glb`, `.png`, `.ogg`), and commit `.import` metadata (but not the `.godot/` cache).
- **Alternatives**:
  - (a) Keep raw sources (Blender/Substance/PSD/WAV masters) in a separate store (Google Drive/OneDrive the developer already has, or Cloudflare R2/Backblaze B2 free tiers, via `rclone`), and record the exact asset version in a manifest file in git.
  - (b) GitLab or Azure DevOps for LFS-heavy repos, if quotas there are larger. Not verified.
  - (c) Moving to GitHub Team raises LFS to 250 GiB but costs per seat, so it isn't zero-cost.
- **Asset licence register**: keep `assets/LICENSES.csv` (or `.md`) in git with one row per third-party or AI-generated asset. Columns: asset path(s), source URL, author, licence (CC0/CC-BY/royalty-free/custom), attribution text, commercial-use OK (y/n), modification OK, date acquired, proof (receipt/screenshot path), AI tool and prompt (if generated), reviewer. Add a CI check that fails when a file under `assets/` has no register row. That matters for ad-network and store reviews (fonts, music, Lagos landmarks/brand logos on buses) and for AI-agent-generated content.
